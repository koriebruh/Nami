> **Status:** outline. Nothing of RUM is merged. Next: NAMI-RUM-1, once Error tracking (its whole sub-project) has merged; step-level code is written at phase start against the then-current `main`.
> **Branch:** `feat/rum-part1` in `.worktrees/rum-part1/`.
> **Depends on:** Error tracking (applications, the in-process event pipeline, `error_events.rum_session_id`), Metrics Part 2 (the shared alert evaluator `incidents::alerting`, NAMI-MET-19), Incidents Part 1 (`incidents::lifecycle`, NAMI-INC-1, NAMI-INC-7, NAMI-INC-10). Metrics Part 1 UI pieces (NAMI-MET-10) are reused. Part 2 (`docs/superpowers/plans/2026-10-24-rum-part2.md`, session replay) follows this phase.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Give Nami Better Stack's RUM minus session replay: RUM applications with public client keys and allowed origins, a small JavaScript SDK built and served by Nami, a cookieless beacon ingest on the public listener, page views, web vitals (LCP, CLS, INP, TTFB, FCP), custom events and identify, JS errors forwarded into Error tracking, website analytics (visitors, visits, referrers, UTM, pages, countries, browsers, OS, devices), web vitals p75 per URL group with alerts that open incidents, funnels, per-user erasure, and the nami-ui pages for all of it.

**Architecture:** A new engine domain `rum/`. Applications live in Postgres (`rum_apps`). The SDK (`nami-rum/`, TypeScript, bundles `web-vitals`) is built with vite into `nami-ui/src/lib/rum/sdk/v1/` together with an SRI manifest, and nami-ui serves it at `/rum/v1/nami-rum.js` from a `+server.ts` outside the `(app)` group. The SDK reads its app config from `GET /api/v1/rum/config`, queues events in memory and sends them to `POST /api/v1/rum/ingest` on the engine's public listener as `text/plain` JSON (sendBeacon, `fetch` keepalive as fallback). Ingest checks, in order of cost: key shape, per-IP bucket, a place, the app (in-memory cache), the `Origin`, the per-app bucket, DNT/GPC, content type, size, JSON, event count and the daily cap. It then enriches each batch in memory (client IP through the trusted-proxy rule, daily-salted visitor hash, GeoIP country from a local `.mmdb`, browser, OS and device from the User-Agent, bots dropped), discards the IP, writes `rum_events` rows to ClickHouse with the logs async-insert settings, and hands `error` events to Error tracking's in-process pipeline. Analytics, vitals and funnels are read-only ClickHouse queries built from static fragments with bound values, under per-user query slots. Vital alerts are one more alert kind of the shared evaluator `incidents::alerting` and open incidents with `source = 'rum_alert'`. A `rum::worker` loop flushes usage counters, prunes rate-limit buckets and deletes salts older than 48 h.

**Tech Stack:** Rust 2024 (Axum 0.8, SQLx 0.9 runtime queries, tokio, `sha2`, `rand` 0.8, `flate2`, `url` 2.5), ClickHouse over HTTP (`core::clickhouse::ClickHouse`), Postgres 17, SvelteKit + Svelte 5 runes + Tailwind 4, vitest. **One new crate:** `maxminddb@0.32.0` (R-RUM1-7). **New npm package `nami-rum/`** with one runtime dependency `web-vitals@6.2.3` and dev dependencies `vite`, `typescript`, `vitest` at the exact versions in nami-ui's lockfile on the phase start commit, plus `jsdom@30.1.2` (R-RUM1-14). No CDN.

**Spec:** `docs/superpowers/specs/2026-10-13-rum-design.md`, the whole file, except "Session replay" and the Sessions UI, which are Part 2. The JS error half of the Error tracking spec (`docs/superpowers/specs/2026-10-13-error-tracking-design.md`) defines what forwarded errors go through. Roadmap: `docs/superpowers/roadmap.md` section 9.

**When to start:** after Error tracking has merged, from the latest `origin/main`. Metrics Part 2 and Incidents Part 1 merge before Error tracking in the sub-project order, so they are on `main` by then. Every reused piece below is named by its planned path and task. ## Why two parts

One phase PR for all of RUM would carry 20 tasks, two new npm packages beside `web-vitals` (rrweb's recorder and player), a browser-test runner, a second binary ingest path with its own decompression-bomb surface and an HTML player that renders hostile recorded pages under its own CSP. Part 1 alone is already 15 tasks, the size of Metrics Part 1. Session replay is independent of everything in Part 1 except the app row and the SDK core, and its threat model (stored XSS through recorded DOM, gzip bombs, very large reads) needs its own security wave. So replay, the sessions list and timeline, and replay erasure are Part 2 (NAMI-RUM-16..20).

## Global Constraints

- All infrastructure runs as containers from `nami-engine/docker-compose.yaml` (Postgres on host port 5433). Never install anything natively.
- Engine test command: `cd nami-engine && DATABASE_URL=postgres://nami:nami@localhost:5433/nami cargo test --test rum <file>::`. UI: `cd nami-ui && npm run check && npx vitest run <files>` (0 errors, 0 warnings). SDK: `cd nami-rum && npm run check && npx vitest run && npm run build`, then `git diff --exit-code nami-ui/src/lib/rum/sdk` (the committed build is the build of the committed source).
- SQLx runtime queries only, SQL as string literals, values bound. ClickHouse SQL only from `&'static str` fragments through `logs::query::Sql`, every value bound, the project and app ids from the path (or from the client key's app row at ingest), never from a body.
- `docs/STANDARDS.md` applies in full, with one recorded exception: the beacon body is parsed leniently (unknown fields and unknown event types are dropped, as the spec says), so it does not use `deny_unknown_fields`. Every management API body does.
- Spec values, verbatim, and where they land:
  - apps: `client_key` = `nami_rum_` + 24 random bytes base64url, public; `allowed_origins` required, 1-20 exact origins; optional `error_app_id`; `session_sample_rate` 0-1 default 1; `replay_sample_rate` 0-1 default 0; `replay_mask_all_text` default false; `respect_dnt` default true; `retention_days` default 90; `replay_retention_days` default 30; `daily_event_cap`; `daily_replay_bytes_cap`; members manage, admins delete (NAMI-RUM-1);
  - SDK: `/rum/v1/nami-rum.js`, budget 12 KiB gzip, bundles `web-vitals`, `Access-Control-Allow-Origin: *`, snippet with its SRI hash; `NamiRUM.init({clientKey, endpoint, release?, environment?, storage?})`; page views on load, History API and `popstate`; `page_leave` with engaged time on `visibilitychange` to hidden; LCP, CLS, INP, TTFB, FCP with value, rating, navigation type; `error` and `unhandledrejection` as Sentry-shaped events; `track(name, props)` with name <= 64 chars, <= 20 props, values <= 256 chars; `identify(userId, traits)` with <= 10 traits; flush every 5 s, at 50 events and on page hide; session id random 128-bit in `sessionStorage`, new after 30 min idle, `storage: false` keeps it in memory; never a cookie; with `respect_dnt` nothing when `navigator.doNotTrack === "1"` or `navigator.globalPrivacyControl` is true (NAMI-RUM-6);

  - analytics: path without query string and fragment, UTM kept apart, host, referrer host and path with own origins excluded, `utm_source|medium|campaign|term|content`, country, browser, OS, device; visitors (unique per day, longer ranges sum daily uniques), visits (page views of one visitor hash with gaps < 30 min), page views, bounce rate, visit duration from engaged time, time series, top pages, entry and exit pages, referrers, UTM values, countries, browsers, OS, devices; `GET /projects/{id}/rum/apps/{app_id}/analytics`, viewer (NAMI-RUM-7);

## Review Focus

- **The client key is public; the origin check is not authentication.** It only limits casual abuse. Every cap (per IP, per app, daily) must hold for a client that forges `Origin` with curl -> NAMI-RUM-4 (`a_forged_origin_still_meets_the_per_ip_and_daily_limits`).
- **A raw IP must never reach a row or a log line.** That includes `X-Forwarded-For` text, error events forwarded to Error tracking and `tracing` fields -> NAMI-RUM-4, NAMI-RUM-5 (`no_stored_row_or_log_line_contains_the_client_ip`).
- **The visitor hash must not be linkable across days.** A salt row older than 48 h must be gone and the same visitor must hash differently on two days -> NAMI-RUM-2, NAMI-RUM-10.
- **Behind a reverse proxy, every visitor looks like the proxy.** The trusted-proxy rule (R-RUM1-1) must take the client address from `X-Forwarded-For` only when the TCP peer is a configured proxy -> NAMI-RUM-4.
- **Analytics text is attacker-chosen.** Paths, referrers, UTM values, props and user ids reach SQL only as bound values and the UI only as escaped text -> NAMI-RUM-7, NAMI-RUM-12.
- **Forwarded JS errors must not bypass Error tracking's limits or scrubbing**, and an app may only link an error app of its own project -> NAMI-RUM-1, NAMI-RUM-5.
- **The SDK runs on customer pages.** It must never set a cookie, never throw into the host page, stay under 12 KiB gzip and do nothing at all under DNT or GPC when the app respects them -> NAMI-RUM-6.

## Decisions the spec leaves open (rulings)

- **R-RUM1-1 Client IP behind a proxy.** The visitor hash and the per-IP limit need the browser's address, but behind a reverse proxy the TCP peer is the proxy, and trusting `X-Forwarded-For` blindly lets any client forge it. New config `PUBLIC_TRUSTED_PROXIES` (comma-separated CIDRs, default empty) and a pure helper `core::client_ip::client_ip(peer, headers, trusted) -> IpAddr`: when the peer is not in a trusted range the peer is the client; when it is, the client is the right-most `X-Forwarded-For` entry that is not itself trusted (an unparsable entry ends the walk and the peer is used). IPv4-mapped IPv6 is normalized to IPv4. CIDRs are parsed by hand (address, `/`, prefix), no crate. With the default, a deployment behind a proxy counts every visitor as one: the setup docs and the app page say so. The private API's own forwarded-address handling is untouched (Platform's job).
- **R-RUM1-2 Missing or `null` Origin is 403.** Browsers send `Origin` on every cross-origin POST and on sendBeacon. A request without one, or with `Origin: null`, is refused like a foreign origin. Origins compare after normalization (lowercase scheme and host, default port removed).
- **R-RUM1-3 Allowed origin format.** `scheme://host[:port]` with scheme `http` or `https`, no path (a single trailing `/` is stripped), query, fragment or userinfo, at most 255 chars, no wildcard. Duplicates after normalization are a 400. `http://localhost:<port>` is allowed for development.
- **R-RUM1-4 SDK config endpoint.** The SDK must know `respect_dnt` and the sample rates before it sends anything, and sendBeacon cannot read a response. `GET /api/v1/rum/config?k=<key>` (public listener, same key, origin and per-IP checks as ingest) answers `{"session_sample_rate", "replay_sample_rate", "replay_mask_all_text", "respect_dnt"}` with `Cache-Control: public, max-age=300` and `Vary: Origin`. It stores nothing. When it fails, the SDK does nothing for that page load.
- **R-RUM1-5 Sampling.** `session_sample_rate` is drawn once per session in the SDK (`Math.random() < rate`) and kept with the session. An unsampled session sends nothing. Analytics are not extrapolated; when the rate is below 1 the analytics response carries `"sampled": true` and the UI says counts are sampled.
- **R-RUM1-6 Beacon schema details.** Batch fields: `session_id` and `page_view_id` (32 lowercase hex, required), `sent_at` (client ms epoch), `release` (<= 200 chars), `environment` (<= 64), `user_id` (<= 128, set after `identify`). An event may carry its own `page_view_id` (web vitals reported after an SPA navigation belong to the hard page load). Each event's `ts` is mapped to server time as `received_at - clamp(sent_at - ts, 0, 1 h)`, so client clock skew does not move events; an event older than 1 h by its own clock is dropped. Event-level limit violations (name over 64 chars, more than 20 props, a value over 256 chars, more than 10 traits, a URL over 2,048 chars, a vital out of range) drop that event and count it as `invalid_events`; the batch is still accepted. Prop and trait values are strings; numbers and booleans are stringified; anything else drops the event. Prop keys are 1-64 chars.
- **R-RUM1-7 GeoIP crate.** Reading the MaxMind DB format is not a few lines, so the engine adds `maxminddb@0.32.0` (default features, no mmap, so no `unsafe`). The file named by `GEOIP_DB_PATH` is read once at startup (`Reader::open_readfile`); an unreadable or invalid file stops startup with a clear error; replacing it needs a restart (documented). Private, loopback and unknown addresses give `unknown`.
- **R-RUM1-8 User-Agent parsing without a crate.** A coarse family classifier is a small table, so it is hand-written in `rum::enrich::ua`: browser `Edge|Opera|Samsung Internet|Firefox|Chrome|Safari|Other`, OS `Windows|macOS|iOS|iPadOS|Android|ChromeOS|Linux|Other`, device `desktop|mobile|tablet|other` (tablet for iPad or for Android without `Mobile`). Bots: an empty User-Agent or one containing any entry of a `const` list (`bot`, `crawl`, `spider`, `slurp`, `headless`, `lighthouse`, `pagespeed`, `preview`, `facebookexternalhit`, `curl/`, `wget/`, `python-requests`, `go-http-client`, `okhttp`, `java/`, `phantomjs`, `puppeteer`, `playwright`, `selenium`), case-insensitive. A bot batch is answered 202 and dropped (`bot_batches`).
- **R-RUM1-9 URL group is computed once, at ingest.** The DDL gains `url_group String` (spec deviation): one Rust function `rum::enrich::url_group(path)` replaces a segment that is all digits, a UUID (8-4-4-4-12 hex), or 12 or more hex chars with `:id`. Alerts, the vitals table and the UI then agree by construction. `navigation_type` has no column: it is stored as `props['navigation_type']`.
- **R-RUM1-10 Server-side rating.** The server recomputes each vital's rating from the web.dev thresholds (good at or below the first, poor above the second) and ignores the client's `rating`, so the split never depends on a client.
- **R-RUM1-11 Reuse of logs ingest pieces.** `TokenBuckets` becomes generic over its key (`TokenBuckets<K = Uuid>`), so the per-IP limiter reuses it; the logs call sites do not change. The per-IP key is the IPv4 address or the IPv6 /64. `logs::ingest::read_body` gains a `max_bytes` argument (logs pass `MAX_BODY_BYTES`). The RUM worker calls `prune_full` on both RUM bucket maps every 60 s.
- **R-RUM1-12 Bounds the spec does not give** (named constants, tests at and past each): per-IP burst `IP_BURST = 40`; `MAX_RUM_IN_FLIGHT = 64` places on the public listener; `MAX_APPS_PER_PROJECT = 20` (409); app `name` 1-100 chars, unique per project (409); `retention_days` 1-365; `replay_retention_days` 1-90; `daily_event_cap` 1,000-100,000,000, default 1,000,000; `daily_replay_bytes_cap` 1 MiB-100 GiB, default 1 GiB; `MAX_ERRORS_PER_BATCH = 10` (more are dropped); app cache TTL 10 s, at most 4,096 entries (settings changes reach ingest within 10 s); analytics, vitals and trend ranges at most 366 days, funnels at most 90 days; breakdown rows default 10, at most 100; vitals table at most 200 groups; `MAX_RUM_QUERIES_PER_USER = 4` (429); `MAX_VITAL_ALERTS_PER_APP = 50` and `MAX_FUNNELS_PER_APP = 50` (409).
- **R-RUM1-13 Daily cap accounting.** Accepted events count in memory per app and flush every 10 s to `rum_app_usage_daily` (the logs usage pattern). A batch is admitted while `flushed + pending < daily_event_cap`; it may overshoot by one batch per engine instance, documented. Over the cap: 429 with `Retry-After` until UTC midnight. Rate limits answer 429 with `Retry-After: 1`. DNT, GPC and bot batches answer 202 with `{"accepted": 0}` so clients do not retry.
- **R-RUM1-14 SDK build and pins.** `nami-rum/` is built with vite library mode (IIFE, global `NamiRUM`, minified, target `es2019`) at the vite, typescript and vitest versions of nami-ui's lockfile, so the repo adds no second bundler. Runtime dependency `web-vitals@6.2.3` (standard build, not attribution), tests with `jsdom@30.1.2`; all installed with `--save-exact`, lockfile committed. `npm run build` writes `nami-ui/src/lib/rum/sdk/v1/nami-rum.js` and `manifest.json` (`{"nami-rum.js": {"sri": "sha384-...", "gzip_bytes": n}}`), both committed. nami-ui imports them with `?raw` and serves them.
- **R-RUM1-15 SDK URL, cache and freezing.** nami-ui serves `/rum/v1/<file>` from `src/routes/rum/v1/[file]/+server.ts`, outside `(app)` (no session, no cookie read or set), with `Content-Type: text/javascript; charset=utf-8`, `Access-Control-Allow-Origin: *`, `Cross-Origin-Resource-Policy: cross-origin`, `X-Content-Type-Options: nosniff`. An SRI-pinned snippet breaks the moment the bytes behind its URL change, so the v1 file is **frozen when RUM Part 2 merges** (Part 2 adds the replay loader to the core first). Until then Part 1 serves it with `Cache-Control: public, max-age=300`; the Part 2 merge switches to `public, max-age=31536000, immutable` and pins the file hash in a test. After the freeze any change ships as `/rum/v2/`, and v1 stays served. Snippets copied between the two merges must be copied again (Part 1 decisions doc and setup page note).
- **R-RUM1-16 The SDK never preflights.** Both sendBeacon and the `fetch` fallback send `Content-Type: text/plain;charset=UTF-8` with `credentials: 'omit'`, so the browser never sends a preflight. The engine still answers `OPTIONS` on both RUM paths for other clients: allowed origin -> 204 with the echoed origin, `Access-Control-Allow-Methods: GET, POST`, `Access-Control-Allow-Headers: content-type`, `Access-Control-Max-Age: 600`, `Vary: Origin`; other origins -> 403. No RUM response ever carries `Access-Control-Allow-Credentials` or `Set-Cookie`.
- **R-RUM1-17 GPC on the server too.** The Privacy section says DNT and GPC are honored on the server: with `respect_dnt`, `DNT: 1` or `Sec-GPC: 1` drops the batch (counted `dnt_batches`).
- **R-RUM1-18 Own origins in referrers.** A referrer whose origin is in `allowed_origins` is stored as empty host and path (internal navigation). A page URL whose origin is not in `allowed_origins` drops the event (`invalid_events`), so a page cannot report another site's paths.
- **R-RUM1-19 Visit attribution.** Visits are built per visitor hash within one UTC day (a visit across midnight counts twice, documented). Referrer and UTM are visit attributes taken from the visit's entry page view; filters on them select whole visits. Path and host filters select page views, and visits are built from the remaining ones. Country, browser, OS and device are constant per visitor hash. Visit duration is the sum of `engaged_ms` of the `page_leave` rows whose `page_view_id` belongs to the visit (the SDK sends a delta on every hide, so the sum is the engaged time), averaged over visits.
- **R-RUM1-20 Vital alert semantics.** One p75 over every event whose `url_group` matches the pattern (glob, `*` = any run of chars) and the device, over `window_seconds` ending at evaluation time; breaching when `p75 > threshold` (threshold in ms, unitless for CLS); fewer than `min_samples` samples = no data with `no_data = keep` fixed; `incident_mode = per_alert` only; evaluated every 60 s; `window_seconds` 300-86,400, default 3,600; `min_samples` 1-100,000; alert `name` 1-100 chars; threshold > 0 and within the vital's range. An `escalation_policy_id` or `severity_id` of another project is a 400. Incidents: `rum_alert_id` with `on delete cascade` (the `log_alert_id` precedent), title `<name>: p75 <VITAL> <value> above <threshold>`, metadata `{app_id, vital, url_group_pattern, device, p75, samples}`. Disabling an alerting alert resolves its incident with reason `alert disabled` (the log alert ruling of Incidents Part 1).
- **R-RUM1-21 Funnel details.** Steps are `{"kind": "page", "path": "..."}` (1-256 chars, starts with `/`, `*` the only wildcard, matched with `LIKE` after escaping `%`, `_` and `\`) or `{"kind": "event", "name": "..."}` (1-64 chars). `window_seconds` 60-14,400, default 3,600. `windowFunnel` in its default mode (other events may come between steps), grouped by `session_id`, empty session ids excluded. Funnel `name` 1-100 chars.
- **R-RUM1-22 Erasure scope and shape.** Events sent before `identify` carry no user id, so erasure removes every event of every session in which that user id appears, plus any row with that user id. A lightweight delete is a mutation, and an `IN` subquery on the same table can be re-evaluated per part and miss rows, so the ids are read first and bound: the route loops `select distinct session_id ... where user_id = {u} limit ERASE_BATCH_IDS` (`ERASE_BATCH_IDS = 500`, because parameters travel in the URL), then a lightweight delete on `rum_events` with `user_id = {u} OR session_id IN {ids:Array(String)}` (project and app bound), until no session is left. Synchronous, capped at 120 s in total, idempotent (a retry continues where it stopped). It answers 200 `{"sessions": n}` (the sessions erased). The user id is 1-128 chars, percent-decoded from the path. Forwarded error events stay in Error tracking with its retention (open question 2). App deletion erases the app's ClickHouse rows the same way after the Postgres delete; a failure there is logged and the TTL removes the rest. The ClickHouse client gains `ClickHouse::mutate_with` (bound parameters, no read-only guard), used only by these deletes.
- **R-RUM1-23 No access log to exclude.** The engine has no per-request access log today. RUM code never puts an address in a `tracing` field (only `app_id`), and a test checks it with a scoped subscriber (`tracing::subscriber::with_default`, thread-local, so it stays in the domain test target). An access log added later (Platform) must skip `/api/v1/rum/*`.
- **R-RUM1-24 Retention changes.** `retention_days` is copied onto each row at ingest (`logs` pattern), so a change applies to new events only, documented on the settings page.

## Open questions (defaults in force until the owner rules)

1. **Trusted proxies (R-RUM1-1).** Default: an explicit `PUBLIC_TRUSTED_PROXIES` list, empty by default, so a proxied deployment must set it or every visitor counts as one. Alternative: reuse whatever Platform adds for the private API.
2. **Erasure of forwarded errors (R-RUM1-22).** Default: user erasure covers `rum_events` (and replays in Part 2) only; error events forwarded into Error tracking keep its retention. Alternative: also delete `error_events` rows with those `rum_session_id`s, which leaves issue counters off.
3. **Client key rotation.** The spec has none; the key is public. Default: no rotate endpoint; a leaked key is limited by `allowed_origins` and the caps, and a new app gives a new key.
4. **Usage page.** Default: the app page shows today's events and replay bytes only; a per-day usage view waits for Platform's usage page.
